# AGENTS.md — TrainPilot

## Commands
- Install: `uv sync` (requires Python >=3.10, repo pins 3.13 in `.python-version`). This is the control-plane install. GPU integrations need only a skill + remote MCP config: `python3 -I -S scripts/install_agent.py install <agent>` (stdlib only, no package install), or Claude Code's GitHub marketplace.
- Test all: `uv run pytest` (`pythonpath=["src","."]`, `testpaths=["tests"]` per `pyproject.toml`)
- Single test: `uv run pytest tests/test_mailbox.py -v` (or `-k <name>` for one case)
- E2E sim (needs server running): `./start.sh` then `uv run python examples/mock_training.py [gateway_url] [task_id]`
- Regenerate the checked-in Claude plugin assets (stdlib only, no venv needed): `python3 -I -S scripts/build_plugins.py`
- GPU install without installing packages: `python3 -I -S scripts/install_agent.py install <agent>`
- Server: `./start.sh` (foreground) / `./start.sh --daemon` / `./start.sh --status` / `./start.sh --stop`; overrides: `-p <PORT>`, `-H <HOST>`
- Docker: `docker build -t trainpilot:latest .` + `docker run -d -p 28780:28780 -v $(pwd)/trainpilot.db:/app/trainpilot.db -v $(pwd)/.env:/app/.env:ro --restart always trainpilot:latest`
- No lint/typecheck/CI configured — pytest is the only verification.

## Architecture
- `src/trainpilot/server/` — FastAPI control plane; entrypoint `trainpilot.server.main:app` (`trainpilot-server`). Key files: `main.py` (mounts Streamable HTTP MCP at `/mcp`), `mcp_server.py` (5 tools: `report` [unified milestone/alert/completed/failed; response always carries `next_task_plans`], `poll_instruction`, `ack_instruction`, `get_task_status`, `ack_plan`; `task_id` optional, falls back to `settings.task_id`; no resources), `mailbox.py` (in-memory scheduler + long-poll wakeup), `plans.py` (`PlanRegistry` for Feishu-queued next-task plans), `storage.py` (SQLite WAL), `cleanup.py` (task & retention cleanup service), `config.py` (pydantic-settings, prefix `TRAINPILOT_`), `routes/` (operator REST only), `feishu/` (`inbound.py` parses inbound `im.message.receive_v1` events).
- `src/trainpilot/agent/` — GPU-side integration, and nothing else: the package is the control plane. There is no TrainPilot Python client and no GPU-side CLI — the agent's own MCP client talks to `/mcp`, and the GPU node installs a skill plus one remote MCP entry. `agent/__init__.py` is a docstring only; everything here is `plugin/`.
- `src/trainpilot/agent/plugin/` — the GPU-side agent plugin. `catalog.py` is a declarative table of supported agents (paths, transport-key spelling, registering command, `docs_url`); `templates.py` holds the only copy of the skill/command/rules prose; `render.py` is pure (context in, `Bundle` out); `install.py` writes bundles safely (merge, backup, dry-run, revert); `commands.py` is the `plugin` command group (`list`/`install`/`uninstall`/`render`) that `scripts/install_agent.py` drives; `release.py` derives the publishable Claude marketplace assets from the same renderer. Adding an agent = one catalog entry + one renderer.
- `src/trainpilot/common/` — `states.py` (`TaskState`: RUNNING→WAITING→RESOLVED→RECOVERING→RUNNING/COMPLETED/FAILED; `ActionType`: `stop_training`/`self_resolve`/`custom` — the actions an agent can receive; the alert card's `wait_for_arrangement` button is a `WAIT_FOR_ARRANGEMENT` module constant instead, since it is a card-only control action that is never delivered to anyone), `schemas.py`, `gateway.py` (address resolution, shared by server+agent).
- Endpoints: `/mcp` (MCP), `/docs`, `/health`, `/ready`, `/webhook/feishu`, `/api/tasks/...`.

## Gotchas
- **Every agent spells "remote MCP server" differently, and the wrong spelling fails silently.** `catalog.py` records each spelling with the vendor `docs_url` it was read from, and `tests/test_plugin_catalog.py` pins them: Antigravity takes `serverUrl` and *rejects* `url`/`httpUrl`; Gemini CLI takes `httpUrl` (its `url` means SSE); Claude Code needs `type: "http"` beside `url` or the entry is read as stdio; Codex is a `[mcp_servers.x]` TOML table; OpenCode is `mcp.servers.<name>` — the flat `mcp.<name>` its docs still show is deprecated, and that entry is `additionalProperties: false`, so an `enabled` key there is rejected at load (opencode's own `config.json` schema is the authority; verify against the installed CLI, not the docs page). Never "harmonise" one target onto another's spelling.
- **The plugin must not restate the supervision protocol.** The contract lives in `mcp_server._INSTRUCTIONS` + the tool docstrings. Skills/commands use the agent's native remote MCP connection and initialization `instructions`, and name no TrainPilot command at all — the GPU node installs no Python, so there is no CLI to fall back on (deleting `agent/cli.py` + `agent/mcp_client.py` is what that costs; `tests/test_plugin_packaging.py` asserts the base dependency list stays empty and the only entry point is `trainpilot-server`). Keep installation imports stdlib-only (lazy schema exports); test with `python -I -S`. Generate checked-in Claude marketplace assets with `python3 -I -S scripts/build_plugins.py`; do not hand-edit generated prose. `tests/test_plugin_catalog.py` and `tests/test_plugin_bootstrap.py` pin these contracts.
- **The published Claude plugin pins its version**, so a prose change without a `trainpilot.__version__` bump leaves marketplace users on the old copy: regenerate assets (`scripts/build_plugins.py`) and bump the version in the same change. `plugin.json`'s version comes from `trainpilot.__version__`; the checked-in tree is generated, never hand-edited.
- **The installer edits files the user owns** (`config.toml`, `opencode.json`, `AGENTS.md`). It merges rather than replaces (marker blocks for TOML/Markdown, deep-merge for JSON), refuses to touch a JSON file that will not parse instead of clobbering it, backs up to `.trainpilot.bak` on every change, and `uninstall` reverses surgically. `tests/test_plugin_install.py` runs everything under a throwaway `$HOME` — never point these tests at a real one.
- **Server dependencies live in the `server` extra *and* the `server` dependency group**, because uv has no `default-extras` (verified: 0.11.26 rejects the key). The base dependency list is **empty** on purpose: the GPU side installs no Python, so everything (`fastapi`, `lark-oapi`, `mcp`, `pydantic`, `pydantic-settings`, `uvicorn`) is the control plane's. The two lists are pinned equal by `tests/test_plugin_packaging.py`; add a server dependency to both or neither. `start.sh` and the `Dockerfile` pass `--group server` explicitly so an inherited `UV_NO_DEFAULT_GROUPS` cannot produce a control plane that will not boot.
- **Single worker only.** Mailbox long-poll locks are in-process; never pass `--workers >1` to uvicorn (`start.sh` and `Dockerfile` already enforce this; scale via `task_id`-hash proxy).
- **`TRAINPILOT_HOST` has dual meaning** (`common/gateway.py`, `server/config.py`, `start.sh:resolve_bind_host`): server side = bind address (only local values `0.0.0.0`/`127.0.0.1`/`localhost` honored, public IP silently falls back to `0.0.0.0`); GPU side = gateway host. Server bind → use `TRAINPILOT_BIND_HOST`; client URL → use `TRAINPILOT_GATEWAY_URL` (highest priority) or `TRAINPILOT_HOST`+`TRAINPILOT_PORT`. Never copy a public IP into the server's `TRAINPILOT_HOST` expecting it to bind.
- **`.env` is per-machine, two modules** (`cp .env.example .env`; `start.sh` auto-creates it): Module 1 = public server, Module 2 = GPU client. Defaults: port `28780`, alert timeout `30s`, long-poll `20s`.
- **The agent-facing contract lives in exactly one place:** `mcp_server._INSTRUCTIONS` plus the five tool docstrings. README and AGENTS.md must point at it, never restate the rules — duplicated rule text is what drifts.
- **Task rows are created only by `report`/`record_event`.** Never build task state from a request path, header, or client IP; reading an unknown `task_id` must return not-found, not fabricate a `RUNNING` row. The plan path reaches the task table **read-only**: `PlanRegistry.register` refuses a plan that names no task or a task with no row, and never calls `record_event`/`_get_or_create` (`tests/test_plans.py::test_registering_a_bound_plan_does_not_create_a_task_row` pins it). There is no global plan: a plan is bound to exactly one task or it is not stored, because a plan no report ever carries is invisible for good and exempt from cleanup.
- **Next-task plans: `@bot` in the group *is* the trigger — there is no keyword prefix**, by explicit product decision. Inbound parsing lives in `server/feishu/inbound.py` (pure, no I/O); `routes/webhook.py` must branch on `is_message_event(data)` *before* the card-action early return. Idempotency is `UNIQUE(source_message_id)` + `INSERT OR IGNORE`, and the receipt card is dispatched only when the row was actually created — Feishu redelivers events it cannot confirm in ~3s. A refused plan (`PlanBindingError` → `build_plan_card(reason=...)`, `card_type="plan_rejected"`) stores nothing, so it has no row to de-dupe against and a redelivery sends a second receipt — the same trade-off the `#fix` rejection already makes. `PlanRegistry` reuses `default_mailbox._storage` (one connection, one lock, and it inherits conftest's DB redirect) — never open a second `SQLiteStorage`. Pending plans are exempt from cleanup (`delete_expired_plans` only reaps acked ones), so `report` keeps re-surfacing them until `ack_plan` or a clear command. Plans go into `report` under `next_task_plans`/`next_task_plans_guidance`; alert's `next_action`/`guidance` keys are a separate, test-pinned contract — do not merge them. The same inbound parser also recognises `#fix(任务名) <方案>` (dispatched as the alert's decision, `action="custom"`, solution in `payload["solution"]`) and `#feat(任务名) <计划>` (identical to the bare `#任务名` tag); `#fix` is parsed first and wins, and its body is kept verbatim. The bare tag accepts CJK (`_TASK_TAG_RE`) so a Chinese task name binds like an ASCII one instead of silently degrading into prose — keep the literal `-` escaped, `/-` in the class otherwise reads as a range bound.
- **`#fix` is gated inside the mailbox, never in the webhook.** `TaskMailboxManager.submit_fix_decision` does the state check *and* the `source_message_id` de-dupe in one critical section under the existing lock, returning `(instruction, created)`; a get-then-submit gate in `routes/webhook.py` would race a concurrent button click. It uses `_get_existing`, so an unknown id raises `TaskNotFoundError` and **no task row is ever created** — the same rule the plan path follows. `tests/test_server_api.py` pins the receipt-card-only-on-`created` behaviour.
- **「等待安排」 is a persisted second auto-resolve stage.** The card click writes `arrangement_requested_at/by` on the task (plain column semantics — NULL means cleared, deliberately *not* the `feishu_message_id` COALESCE), leaves state/`pending_instruction` untouched, and arms `schedule_auto_resolve(stage="arrangement")`. `try_auto_resolve(..., stage=...)` makes the two windows mutually exclusive: the alert stage no-ops while the window is open, the arrangement stage no-ops without it. Any queued instruction closes the window via `_clear_arrangement`, as does a non-duplicate fresh alert — without that, the next alert's 30s timer could never fire again.
- **A card callback must always answer HTTP 200.** Feishu maps *any* non-200 from the callback URL onto the client-side code `200671` (a malformed body is `200672`, an invalid card `200673`) and shows the engineer nothing else, so every refusal on the click path — terminal/unknown task, 「等待安排」 outside an alert, bad Verification Token — is a `200` with an error toast, never a 4xx. `routes/webhook.py::_card_action_shape` classifies the payload first because the two callback generations verify differently: only the v2 `card.action.trigger` payload carries the Verification Token (`header.token`); a legacy v1 payload's top-level `token` is the `c-xxxx` *card-update credential*, so comparing it to `TRAINPILOT_FEISHU_VERIFICATION_TOKEN` 403s every click. `/feishu` and `/feishu/` are both routed — the trailing-slash form would otherwise fall through to the MCP `mount("/")` and 404, another 200671. `tests/test_server_api.py` pins all of these.
- **Do not commit secrets/artifacts.** `.env` (has real tokens), `trainpilot.db*`, `*.log`, `.trainpilot.pid` are gitignored — never `git add` them.
- **Feishu without credentials is safe:** unconfigured → Mock mode logs cards to console. Use `TRAINPILOT_ENABLE_MOCK_FEISHU=true` for local tests.
- **Test isolation is centralized in `tests/conftest.py`** and covers every suite: it redirects `settings.sqlite_path` to a temp DB *before* `trainpilot.server.mailbox` is imported (the default is the relative `trainpilot.db`, and mailbox teardown issues `DELETE FROM tasks` — an unredirected run wipes the local dev database), then resets `default_mailbox` and nulls `api_token`/`feishu_verification_token` around each test. Don't re-declare those fixtures per module. `test_e2e_simulation.py` boots live uvicorn on port `18925`, runs the example in-process, and samples task state from a watcher thread to prove the HITL loop ran.
- **`TaskMailboxManager` exposes only async long polling** (`get_instruction_async`, backed by `_async_instruction_waiters`); the blocking `threading.Event` variant was removed as dead code. Callers inside sync tests must `await` it.
- **`examples/mock_training.py` is imported by a test** (`tests/test_e2e_simulation.py` → `run_mock_training`, resolved via `pythonpath=["src","."]`; `tests/test_mcp_transport.py` reuses its `call_tool`). It drives the tools with the reference MCP SDK and no TrainPilot client, which is also how the wire contract is covered now. Keep it importable and keep the `examples/` directory non-empty — the `Dockerfile` COPYs it.
- **Auth split:** MCP/REST use `Authorization: Bearer <TRAINPILOT_API_TOKEN>` (or `X-API-Token`); `/webhook/feishu` uses `TRAINPILOT_FEISHU_VERIFICATION_TOKEN` instead and is unaffected by API token.
